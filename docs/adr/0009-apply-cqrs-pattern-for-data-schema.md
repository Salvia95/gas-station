# ADR-0009: 데이터 스키마에 CQRS 패턴 적용

## Status

Accepted

## Context

레거시 시스템의 테이블은 하나의 기능에 대해 **읽기와 쓰기를 모두 단일 비정규화 테이블**을 사용해 처리하고 있다. 서비스 요건의 추가에 따라 컬럼과 인덱스가 지속적으로 추가만 되고 있다.

이로 인해 다음과 같은 문제가 발생하고 있다:

- **읽기 성능 하락**: 서비스 기간이 길어짐에 따라 테이블 비대화로 읽기 성능이 점차 하락하고 있다.
- **자원 교착(Deadlock)**: 쓰기 동작 시 비정규화된 넓은 테이블에서 예상치 못한 자원 교착 문제가 발생하고 있다.
- **상충되는 최적화**: 쓰기 최적화(정규화, 인덱스 최소화)와 읽기 최적화(비정규화, 인덱스 추가)가 단일 테이블에서 상충한다.
- **스키마 변경 부담**: 한 쪽 요구사항을 위한 스키마 변경이 다른 쪽에 부정적 영향을 미친다.

## Decision

**CQRS(Command Query Responsibility Segregation)** 패턴을 적용하여 Command와 Query의 역할을 명확히 분리한다.

구체적인 구현 방식은 다음과 같다:

1. **데이터베이스 분리**
    - **Command DB**: 쓰기 작업 전용, 정규화된 스키마
    - **Query DB**: 읽기 작업 전용, 조회 최적화된 비정규화 스키마

2. **데이터 동기화**
    - PostgreSQL의 **Logical Replication**을 활용하여 Command DB의 변경 사항을 Query DB로 동기화한다.
    - 실시간 복제가 아닌 준실시간(Near Real-time) 복제로 Eventual Consistency를 허용한다.

3. **각 DB의 최적화 전략**
    - **Command DB**:
        - 정규화를 통한 체계적인 데이터 관리
        - 쓰기 성능 최적화를 위한 최소한의 인덱스
        - 트랜잭션 무결성 보장
    - **Query DB**:
        - 부분 비정규화를 통한 조회 성능 확보
        - 파티션 적용으로 대용량 데이터 관리
        - 조회 패턴에 맞는 다양한 인덱스 구성

4. **실시간성이 필요한 조회**
    - 주문, 매출 등 실시간 데이터가 필요한 경우 Command DB를 직접 조회한다.

## Consequences

### 긍정적 영향

- 읽기와 쓰기 각각에 최적화된 스키마 설계가 가능해진다.
- Command DB의 정규화로 데이터 일관성과 관리 효율성이 향상된다.
- Query DB의 비정규화와 인덱싱으로 조회 성능이 크게 개선된다.
- 읽기/쓰기 부하를 물리적으로 분리하여 각각 독립적으로 확장 가능하다.
- 쓰기 작업 시 자원 교착 문제가 감소한다.

### 부정적 영향

- 두 개의 데이터베이스를 운영해야 하므로 인프라 복잡성이 증가한다.
- Logical Replication 설정과 모니터링에 대한 운영 부담이 발생한다.
- Eventual Consistency로 인해 읽기 데이터가 최신이 아닐 수 있다.
- 동일 데이터에 대해 두 가지 스키마를 관리해야 한다.

### 중립적 영향

- 사용자의 데이터 이용 패턴 분석 결과, 대부분의 사용자가 조회 전용 서비스를 "실적 관리용"으로 사용하고 있어 실시간 복제가 필수는 아니다.
- Replication Lag 모니터링과 알림 체계 구축이 필요하다.
- 장애 시 Failover 전략 수립이 필요하다.

## Comments
- Query DB의 경우 일 단위 집계를 위한 DW가 존재하기에 Failover가 가능하지만, Command DB의 경우 Standby 상태의 DB를 Active 상태로 바꾸는 방법 뿐이다.
- 정보 수명 관리(Information Lifecycle Management)의 관점에서 개별 DB의 데이터에서 수명이 다한 데이터를 어떻게 폐기, 분리보관할지 고려해야 한다.
