# ADR-0008: 데이터 관계 설계로 FK 기반 정규화 채택

## Status

Accepted

## Context

레거시 시스템의 테이블은 하나의 거래를 식별할 수 있는 다수의 데이터 묶음을 모두 Primary Key(PK)로 설정해 이를 연계되는 모든 테이블에 동일하게 적용하는 **N:N PK 기반 테이블 설계**가 적용되어 있다.

예시:
```
거래_테이블 (거래일자, 점포코드, 거래번호, POS번호, ...) -- 4개 컬럼이 모두 PK
상세_테이블 (거래일자, 점포코드, 거래번호, POS번호, 순번, ...) -- 5개 컬럼이 모두 PK
```

이 설계의 장점과 문제점은 다음과 같다:

**장점**:
- 테이블 스키마 구성의 일관성 확보
- 자동 생성되는 PK 인덱스로 최소한의 조회 속도 보장

**문제점**:
- **관계 불명확**: 데이터만으로는 테이블 간 관계를 명확히 파악할 수 없다.
- **정규화 불가**: 복합 PK의 중복으로 테이블 정규화가 어렵다.
- **ORM 호환성 저하**: JPA 등 ORM에서 복합키 매핑이 복잡하고, 연관관계 설정이 어렵다.
- **변경 비용 증가**: PK 컬럼 변경 시 연관된 모든 테이블을 수정해야 한다.

## Decision

테이블 관계 설계를 N:N PK 기반에서 **단일 대리키(Surrogate Key) + Foreign Key 기반**으로 변경한다.

구체적인 설계 원칙은 다음과 같다:

1. **단일 대리키 사용**: 각 테이블은 비즈니스 의미가 없는 단일 ID(대리키)를 PK로 사용한다.
2. **Foreign Key로 관계 정의**: 테이블 간 관계를 FK로 명시적으로 정의하여 데이터 무결성을 보장한다.
3. **복합 유니크 제약**: 비즈니스적으로 유일해야 하는 조합은 Unique Constraint로 별도 관리한다.
4. **인덱스 전략 수립**: PK 기반 단일 복합 인덱스 대신, 조회 패턴에 맞는 복수 인덱스로 구성하여 조회 속도를 확보한다.

예시:
```
거래_테이블 (id BIGSERIAL PK, 거래일자, 점포코드, 거래번호, POS번호, ...)
           UNIQUE(거래일자, 점포코드, 거래번호, POS번호)
           
상세_테이블 (id BIGSERIAL PK, 거래_id BIGINT FK REFERENCES 거래_테이블(id), 순번, ...)
```

## Consequences

### 긍정적 영향

- FK를 통해 테이블 간 관계가 스키마 레벨에서 명확하게 드러난다.
- 데이터베이스가 참조 무결성을 자동으로 보장한다.
- JPA의 @OneToMany, @ManyToOne 등 연관관계 매핑이 자연스러워진다.
- PK 변경 없이 비즈니스 키 조합을 유연하게 변경할 수 있다.
- 테이블 정규화를 통해 데이터 중복이 감소한다.

### 부정적 영향

- 기존 시스템과의 데이터 연동 시 키 매핑 레이어가 필요하다.
- 조회 시 기존 복합 PK 인덱스 대신 별도 인덱스 설계가 필요하다.
- 기존 데이터 마이그레이션 시 ID 부여와 FK 매핑 작업이 필요하다.
- 비정규화된 테이블에 비해 조회 작업에서 속도가 떨어질 수 있다.

### 중립적 영향

- 비즈니스 키 조회가 빈번한 경우 적절한 인덱스 튜닝이 필요하다.
- ID 생성 전략(IDENTITY, SEQUENCE, UUID 등) 결정이 필요하다.
