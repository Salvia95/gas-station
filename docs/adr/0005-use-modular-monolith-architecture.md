# ADR-0005: 시스템 아키텍처로 모듈러 모놀리스 채택

## Status

Accepted

## Context

레거시 시스템은 전형적인 **"Big Ball of Mud" 형태의 계층형 아키텍처가 적용된 모놀리스 시스템**이다. 하나의 애플리케이션 안에 비즈니스 로직, 도메인, 데이터 접근 등이 전부 결합되어 있고 하나의 프로세스로 배포되는 구조로 되어있다.

이로 인해 다음과 같은 문제가 발생하고 있다:

- **오류 전파**: 강결합으로 인해 하나의 서비스 내에서도 부분의 오류가 전체의 오류로 전파된다.
- **도메인 불일치**: 도메인 영역에 대한 식별이 불가능하여 모든 서비스에서 동일한 도메인이 다르게 정의되고 있다.
- **변경 영향도 파악 불가**: 코드 변경 시 영향 범위를 파악하기 어려워 회귀 버그가 빈번하다.
- **확장성 제약**: 특정 기능만 독립적으로 확장하는 것이 불가능하다.

MSA로의 직접 전환도 고려되었으나, 다음 이유로 적합하지 않다고 판단했다:

- 현재 조직의 기술적 성숙도와 운영 역량으로는 분산 시스템 운영이 어렵다.
- 인프라, 네트워킹, 서비스 구조 등 모든 것이 동시에 변경되어야 한다.
- 도메인 경계가 명확하지 않은 상태에서의 서비스 분리는 "분산형 모놀리스 시스템"을 만들 위험이 있다.

## Decision

시스템 아키텍처를 전통적 모놀리스에서 **모듈러 모놀리스(Modular Monolith)** 로 전환한다.

**Spring Modulith**를 활용하여 다음과 같이 구현한다:

1. **도메인 기반 모듈 분리**: 도메인 주도 설계(DDD)를 적용하여 Bounded Context를 기반으로 모듈을 분리한다.
2. **모듈 경계 검증**: Spring Modulith의 아키텍처 검증 기능을 통해 모듈 간 의존성 규칙을 자동으로 검증한다.
3. **Clean Architecture 적용**: 도메인을 비즈니스 로직과 데이터 접근에서 완전히 격리시켜 프레임워크/아키텍처 변화에도 도메인의 불변성을 보장한다.
4. **이벤트 기반 통신**: 모듈 간 통신은 직접 호출이 아닌 이벤트를 통해 느슨하게 결합한다.

이 접근을 통해 향후 MSA 전환 시 모듈 단위로 점진적 분리가 가능하도록 준비한다.

## Consequences

### 긍정적 영향

- 도메인 경계가 명확해져 코드 변경의 영향 범위를 쉽게 파악할 수 있다.
- 모듈 간 느슨한 결합으로 부분 오류의 전체 전파가 방지된다.
- 단일 프로세스 내에서 동작하므로 분산 시스템의 복잡성(네트워크 지연, 분산 트랜잭션 등)을 회피할 수 있다.
- 향후 MSA 전환 시 모듈 단위로 점진적 분리가 가능하다.
- Spring Modulith의 아키텍처 테스트로 모듈 경계 위반을 자동 탐지할 수 있다.

### 부정적 영향

- DDD, Clean Architecture 등 아키텍처 패턴에 대한 학습이 필요하다.
- 모듈 분리 기준 수립에 많은 설계 노력이 필요하다.
- 모듈 간 이벤트 통신으로 인한 추가 복잡성이 발생한다.
- 전체 시스템이 여전히 단일 프로세스이므로 기술 스택 다양화는 제한된다.

### 중립적 영향

- 기존 코드의 모듈 재배치 작업이 필요하다.
- 팀 구조가 모듈 단위로 재편될 수 있다.
