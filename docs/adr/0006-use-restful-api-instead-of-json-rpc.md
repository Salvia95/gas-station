# ADR-0006: 서비스 호출 방식으로 RESTful API 채택

## Status

Accepted

## Context

레거시 시스템은 개발의 편의를 위해 모태가 되는 시스템의 Client ↔ AP 호출 방식을 그대로 계승하여 서비스 호출에 **서비스코드 기반 JSON-RPC**를 사용하고 있다.

현재 통신 구조의 문제점은 다음과 같다:

- **성능 제약**: HTTP의 POST 방식을 사용해 단일 서비스 포인트에 접근하므로, gRPC 등의 바이너리 통신에 비해 느리다.
- **캐싱 불가**: HTTP 요청에 대한 캐싱이 어려워 RESTful API에 비해서도 상대적으로 느리다.
- **응답 비일관성**: 모든 응답을 HTTP 응답코드가 아닌 body에 적재하는 탓에 응답에 대한 일관성을 유지할 수 없다.
- **표준화 부재**: 서비스코드 기반 라우팅으로 API 문서화, 테스트 자동화가 어렵다.

대안으로 **gRPC**와 **GraphQL**도 고려되었다:

**gRPC 미채택 이유**:
- 타 시스템과의 연동, 외부 기관과의 연계 요건이 다수 존재하여 범용성이 중요하다.
- 현재 JSON-RPC 방식으로도 전체 요청을 충분히 처리할 수 있는 성능을 보여주고 있다.

**GraphQL 미채택 이유**:
- BFF(Backend For Frontend) 구성 없이 도입 시 프론트엔드 복잡도가 과도하게 증가한다.
- 인증, 개인정보 노출 등 보안 관련 부분에서 예기치 못한 문제가 발생할 수 있다.
- 현 시점에서는 RESTful API로 전환 후, 정말 유연한 쿼리가 필요한 부분만 GraphQL로 일부 전환하는 것이 바람직하다.

## Decision

서비스 호출 방식을 JSON-RPC에서 **RESTful API**로 변경한다.

RESTful API를 선택한 이유는 다음과 같다:

1. **범용성**: 거의 모든 클라이언트와 시스템에서 지원하며, 외부 기관 연계에 제약이 없다.
2. **HTTP 표준 활용**: HTTP 메서드(GET, POST, PUT, DELETE)와 상태 코드를 활용하여 일관된 인터페이스를 제공한다.
3. **캐싱 용이**: GET 요청에 대한 HTTP 캐싱이 가능하여 조회 성능을 개선할 수 있다.
4. **문서화/테스트 자동화**: OpenAPI(Swagger)를 통한 자동 문서화와 테스트 도구 연동이 용이하다.
5. **직관적 URL 설계**: 자원 중심의 URL 설계로 API의 의도가 명확하게 드러난다.

## Consequences

### 긍정적 영향

- HTTP 표준 상태 코드를 활용하여 응답의 일관성이 확보된다.
- GET 요청 캐싱을 통해 조회 성능이 개선된다.
- OpenAPI/Swagger를 통한 자동 API 문서화가 가능해진다.
- 외부 시스템과의 연동이 표준화된 방식으로 이루어진다.
- Postman, RestAssured 등 표준 테스트 도구 활용이 용이해진다.

### 부정적 영향

- 기존 JSON-RPC 기반 클라이언트의 호출 방식 변경이 필요하다.
- 리소스 중심 설계로 인해 복잡한 비즈니스 로직 표현이 어려울 수 있다.
- Over-fetching/Under-fetching 문제가 발생할 수 있다.

### 중립적 영향

- API 버전 관리 전략 수립이 필요하다.
- HATEOAS 적용 여부에 대한 추가 결정이 필요할 수 있다.
