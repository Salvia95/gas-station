# ADR-0004: 영속성 프레임워크로 Hibernate + QueryDSL 채택

## Status

Accepted

## Context

레거시 시스템은 영속성 프레임워크로 SQL Mapper인 MyBatis를 사용하고 있다. 복잡한 스키마를 가지는 테이블 간 조인을 쉽게 처리하고, 다양한 집계 함수나 명시적 힌트 사용을 통해 높은 성능을 보장하기 위해 선택되었다.

그러나 다음과 같은 문제가 발생하고 있다:

- **데이터베이스 과의존**: 프레임워크 구조상 비즈니스 로직이 SQL에 과도하게 의존하게 되어, 애플리케이션 계층이 축소되고 있다.
- **테스트 어려움**: 실제 데이터베이스 없이는 테스트가 어려워 실시간성 테스트에 한계가 있다.
- **품질 편차**: 개발자의 쿼리 작성 수준에 따라 서비스 전체의 성능이 결정되어 품질 편차가 크다.
- **도메인 모델 부재**: 테이블 중심의 사고로 인해 객체지향적 도메인 모델링이 어렵다.

## Decision

영속성 프레임워크를 MyBatis에서 **Hibernate + QueryDSL** 조합으로 변경한다.

이 조합을 선택한 이유는 다음과 같다:

1. **Hibernate (JPA 구현체)**
    - ORM을 통한 엔티티 ↔ 스키마 간 매핑으로 도메인 중심 설계가 가능하다.
    - 기본 CRUD 쿼리 자동 생성으로 개발자의 쿼리 작성 능력과 무관하게 일정 수준의 품질을 보장한다.
    - 1차 캐시, 지연 로딩 등 성능 최적화 기능을 기본 제공한다.
    - 변경 감지(Dirty Checking)를 통해 명시적 `UPDATE` 문 없이 엔티티 변경이 가능하다.

2. **QueryDSL**
    - 타입 세이프한 쿼리 작성으로 컴파일 타임에 쿼리 오류를 발견할 수 있다.
    - 복잡한 집계, 다중 조인이 필요한 조회 쿼리를 명시적으로 작성할 수 있다.
    - DTO 프로젝션을 통해 조회 성능을 최적화할 수 있다.

**역할 분담**:
- **Hibernate**: Command 처리 및 간단한 CRUD → 영속성 컨텍스트의 이점 극대화
- **QueryDSL**: 읽기 성능이 중요한 복잡한 조회 → 명시적 쿼리 최적화

## Consequences

### 긍정적 영향

- 도메인 모델을 애플리케이션 계층에서 관리할 수 있어 비즈니스 로직의 응집도가 높아진다.
- 영속성 컨텍스트의 1차 캐시를 통해 반복 조회 성능이 향상된다.
- 변경 감지를 통해 `UPDATE` 쿼리 작성 부담이 감소한다.
- QueryDSL의 타입 세이프 쿼리로 런타임 SQL 오류가 크게 감소한다.
- 데이터베이스 독립적인 코드 작성이 가능해진다.

### 부정적 영향

- N+1 문제, 지연 로딩 등 JPA 특유의 이슈에 대한 이해가 필요하다.
- MyBatis에 비해 학습 곡선이 가파르다.
- 네이티브 SQL이 필요한 복잡한 쿼리(윈도우 함수, 힌트 등)는 별도 처리가 필요하다.
- QueryDSL Q클래스 생성을 위한 빌드 설정이 추가된다.

### 중립적 영향

- 기존 MyBatis 기반 쿼리의 마이그레이션 전략 수립이 필요하다.
- 조회 전용 쿼리와 Command 쿼리의 명확한 분리 기준 정립이 필요하다.
