# ADR-0010: Flyway를 이용한 데이터베이스 스키마 버전 관리

## Status

Accepted

## Context

레거시 시스템의 데이터베이스 스키마 관리는 다음과 같은 프로세스로 진행되고 있다.

1. 개발자가 스키마 변경 요청서를 작성
2. DBA에게 작업 요청 및 승인 대기
3. 승인 후 DBA가 운영 DB에 직접 DDL 실행
4. 변경 내용을 별도 문서(Word, Excel)로 관리

이로 인해 다음과 같은 문제가 발생하고 있다:

- **변경 이력 유실**: 스키마 변경 이력이 체계적으로 관리되지 않아, 특정 시점의 스키마 상태를 파악하기 어렵고 변경 사유가 유실되는 상황이 빈번하다.
- **환경 간 불일치**: 개발, 스테이징, 운영 환경의 스키마가 서로 다른 상태로 유지되어 배포 시 예기치 못한 오류가 발생한다.
- **수기 마이그레이션**: 데이터 마이그레이션이 필요할 시 전체 DB의 데이터를 내려받은 후 Excel 등을 통해 가공하고 직접 데이터를 적재하는 수기 작업이 진행되어 휴먼 에러가 발생한다.
- **롤백 불가**: 스키마 변경에 문제가 발생해도 이전 상태로의 롤백이 체계적으로 불가능하다.
- **코드-스키마 동기화 어려움**: 애플리케이션 코드와 데이터베이스 스키마의 버전이 맞지 않아 배포 순서에 민감해진다.

대안으로 **Liquibase**도 고려되었으나 다음 이유로 Flyway를 선택했다.

- Flyway는 SQL 기반으로 동작하여 기존 DBA와 개발자의 학습 곡선이 낮다.
- Spring Boot와의 통합이 더 간단하고 설정이 직관적이다.
- 단순한 버전 관리가 목적이므로 Liquibase의 XML/YAML 기반 추상화는 오버스펙이다.

## Decision

데이터베이스 스키마 버전 관리 도구로 **Flyway**를 도입한다.

구체적인 적용 방식은 다음과 같다:

1. **마이그레이션 스크립트 관리**
    - 모든 스키마 변경은 SQL 마이그레이션 파일로 작성한다.
    - 파일 명명 규칙: `V{버전}__{설명}.sql` (예: `V1.0.0__create_station_table.sql`)
    - 마이그레이션 파일은 소스 코드와 함께 Git으로 버전 관리한다.

2. **마이그레이션 유형 구분**
    - **Versioned Migration (V)**: 스키마 변경, 한 번만 실행
    - **Repeatable Migration (R)**: View, Function, Procedure 등 반복 실행 가능한 객체
    - **Undo Migration (U)**: 롤백이 필요한 경우 (Flyway Teams 기능)

3. **데이터 마이그레이션**
    - 데이터 변환이 필요한 경우 DML을 포함한 마이그레이션 스크립트를 작성한다.
    - 대용량 데이터 마이그레이션은 배치 처리를 고려한 스크립트로 작성한다.

4. **CI/CD 통합**
    - 애플리케이션 시작 시 자동으로 마이그레이션이 실행되도록 설정한다.
    - PR 단계에서 마이그레이션 스크립트의 문법 검증을 수행한다.

5. **환경별 전략**
    - 개발/스테이징: 애플리케이션 시작 시 자동 마이그레이션
    - 운영: 배포 파이프라인에서 별도 단계로 마이그레이션 실행 (승인 절차 포함)

## Consequences

### 긍정적 영향

- 모든 스키마 변경 이력이 Git에 기록되어 변경 사유와 시점을 명확히 추적할 수 있다.
- 개발, 운영 환경의 스키마가 항상 동일한 상태로 유지된다.
- 데이터 마이그레이션이 스크립트로 자동화되어 휴먼 에러가 감소한다.
- 새로운 환경 구축 시 마이그레이션 스크립트만 실행하면 동일한 스키마를 구성할 수 있다.
- 애플리케이션 코드와 스키마 변경이 동일한 PR에서 관리되어 버전 동기화가 보장된다.
- 코드 리뷰 프로세스를 통해 스키마 변경에 대한 검토가 이루어진다.

### 부정적 영향

- 한 번 적용된 마이그레이션 스크립트는 수정이 불가능하여, 실수 시 새로운 마이그레이션으로 수정해야 한다.
- DBA의 역할이 변경되어 기존 업무 프로세스 조정이 필요하다.
- 운영 환경의 긴급 스키마 변경 시에도 마이그레이션 파일 작성이 필요하여 즉각적인 대응이 어려울 수 있다.
- 대용량 테이블의 스키마 변경 시 락 이슈에 대한 별도 고려가 필요하다.

### 중립적 영향

- 기존 운영 중인 데이터베이스에 Flyway를 적용하기 위한 베이스라인 설정이 필요하다.
- 마이그레이션 스크립트 작성에 대한 팀 컨벤션 수립이 필요하다.
- flyway_schema_history 테이블이 각 데이터베이스에 생성된다.
